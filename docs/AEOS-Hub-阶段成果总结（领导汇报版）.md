# AEOS Hub 阶段成果与后续开发说明

本说明依据《AEOS Hub 后续开发需求文档 v2.0》及当前项目代码整理，用于说明已具备的建设基础、已落地的功能，以及后续开发的明确范围。

## 一、当前结论

AEOS Hub 已完成中枢试点的基础能力建设：能够在只读边界内汇总已批准系统的业务事实、证据、数据时效和风险，并为管理者提供经营事项、任务、证据和核验的基础能力。

后续开发的目标不是增加页面或单个 Agent，而是建立可管理的协同机制：管理者发现跨系统问题后，系统能够将任务分派给合适的责任角色或智能体，持续展示过程和风险，并由业务 Owner 对结果进行验证。

## 四、已落地的后续需求相关能力

### RQ-01 统一任务中心与责任闭环

已建立任务对象、任务状态流转和任务处理基础。任务可记录任务编号、业务对象、证据、优先级、截止时间、发起人、当前主办方、状态和关联编号；已支持任务状态、处理记录、结果提交和业务核验的基础流程。

任务状态已覆盖 DRAFT、ASSIGNED、ACCEPTED、IN_PROGRESS、AWAITING_DECISION、AWAITING_VERIFY、COMPLETED、REJECTED、FAILED、CANCELLED 等核心状态，并保留状态变化的操作者、理由和历史记录。

### RQ-02 系统智能体注册与生命周期管理

已具备智能体和运行实例的登记、状态、健康校验及任务可接单性判断基础。智能体是否可接单会结合生命周期状态、租户适用性、任务类型和运行健康情况进行校验；未处于启用状态或健康校验不通过的智能体不会作为可用主办方。

### RQ-03 智能派单与人工决策控制

已具备对候选智能体的可用性校验以及人工确认、任务分派和结果核验的基础控制。系统保留人工对处理人的选择和调整空间；智能体仅在只读边界内提供分析，不得自行关闭任务或确认业务结果。

### RQ-04 可信身份、证据与结果验证

已具备身份认证、权限控制、Guard、Evidence、Result 和 Verify 的基础能力。结果在业务核验前保持待确认状态；智能体输出不能直接作为已完成的业务结论。关联编号可用于连接事项、任务、结果和证据。

### RQ-06 运行监控与发布门禁基础

已具备运行健康检查、Guard 拒绝处理、任务和运行实例校验等基础能力，并已为任务中心、身份认证、证据、结果和安全控制配置自动化测试。

## 五、当前可直观看到的业务链路

```text
已批准系统的只读事实
          ↓
风险识别与经营事项
          ↓
创建任务、记录证据和关联编号
          ↓
责任角色或候选智能体的可用性校验
          ↓
处理记录与结果提交
          ↓
业务 Owner Verify 或 Reject
```

当前已具备从“事实与风险”进入“任务、结果和核验”的基础链路。后续重点是补齐派单规则、跨系统可靠投递、完整审计和可复制接入标准，使该链路可在真实业务场景中稳定运行。

## 六、后续开发范围

以下内容是需求文档明确要求、但仍需继续完成和验收的建设事项。

| 需求 | 后续交付内容 | 验收重点 |
|---|---|---|
| RQ-01 统一任务中心与责任闭环 | 完善从经营事项创建任务、分派、改派、撤回、催办、补证、升级到验证的完整责任链。 | 管理者能够看到责任人、智能体、进度、证据、阻塞和下一步；超时或失败不能被显示为已完成。 |
| RQ-02 智能体注册与生命周期管理 | 完善 Agent Registry，登记业务 Owner、技术 Owner、数据来源、读写属性、数据时效、版本、状态和下线规则。 | 新增系统智能体可完成登记、测试、发布、暂停和下线，且各步骤可审计。 |
| RQ-03 智能派单与人工决策控制 | 建立可解释的派单规则和人工确认机制。 | 高风险、质量、金额承诺、跨系统写入和规则冲突事项必须经人工确认后派单；数据不足或智能体不可用时应升级给责任角色。 |
| RQ-04 可信身份、证据与结果验证 | 在生产环境接入 M01 身份、组织、角色和租户上下文；通过 M02 可靠投递 Event、Result、Evidence 和 Audit。 | 可按关联编号追溯用户、智能体、对象、任务、决策、结果和证据；只有业务 Owner 可 Verify 或 Reject。 |
| RQ-05 标准接口文档和新系统接入规范 | 建立 Hub OpenAPI、Task/Assignment/Update/Result/Verify JSON Schema、智能体接入规范和联调验收手册。 | 模拟系统智能体可仅按文档完成注册、接单、回传结果和联调验收，无需改动 Hub 核心路由。 |
| RQ-06 运行监控与发布门禁 | 完善日志、指标、告警、契约测试、安全检查、Secret 管理、恢复和版本回退说明。 | 未通过契约或高危安全检查的改动不能发布；关键依赖异常时可区分服务存活、依赖不可用和数据置信度不足。 |

## 七、建议的建设顺序

需求文档已明确后续阶段顺序：

1. **规则冻结**：确认首个业务场景、任务类型、责任角色、智能体范围，以及 M01、M02 的接口责任人。
2. **P0 闭环**：完成任务中心、智能体注册、派单控制、可信身份、证据和验证链路，使一个只读场景完成“发现、分派、办理、决策、Verify”。
3. **P1 标准化**：完成 OpenAPI、任务契约、接入手册、监控和 CI 门禁，使新系统可依据文档独立完成模拟联调。
4. **扩展接入**：在首个闭环稳定且不存在未关闭 P0 问题的前提下，按同一规范接入质量、生产、供应或其他系统智能体。

## 八、当前建设边界

- Hub 是统一入口、受控协同和经营分析平台，不是订单、BOM、质量或库存等专业业务系统的事实源。
- 试点期的系统智能体仅做只读分析和建议，不直接改变业务状态。
- 高风险、质量、金额承诺、跨系统写入和规则冲突事项必须保留人工确认。
- 智能体不能自行将分析结果标记为已验证或已完成；业务 Owner 才能进行 Verify 或 Reject。
- 对缺失、陈旧或不可用的数据，系统必须明确标识数据置信度不足，不能包装为无风险或已完成。

## 九、领导关注结论

AEOS Hub 已具备开展首个只读经营分析场景试点的基础条件。下一阶段的工作重点是把已有的查询、风险识别、证据、任务和核验能力，建设为可追责、可审计、可验证、可复制接入的协同闭环。
