## 1. 交付说明与核验范围

本稿沿用订单、物料齐套、异常与质量、生产协同链路的交接方式，覆盖采购中心的业务目标、现有能力、目标链路、建议接口、字段约束、Evidence、Hub 接入、联调验收、责任分工、上线和回退要求，供中台平台组、采购中心、MCP 开发和 AEOS Hub 开发共同评审。

本次只新增交接文档，不新增采购 Tool、不修改中台业务数据、不创建采购申请或采购订单，也不上线采购页面。当前浏览器入口仍为上述中台地址；采购中心实际菜单、页面路由和业务接口是否已开放，需要由中台管理员登录后提供脱敏页面或接口说明确认。

本文区分三类信息：

- **已实现能力**：以仓库当前 `mcp-company-control/`、`mcp/registry.json` 和 `server.json` 为准，可以证明本地适配器和登记状态。
- **建议新增能力**：为采购链路提出的接口、字段和风险规则，尚未作为中台现有功能的证明。
- **实时经营结论**：必须在实际调用成功后引用 MCP 返回的 `evidence_refs`。本稿没有实时采购业务 Evidence，不填写真实供应商、金额、欠料或交期结论。

## 2. 业务目标与边界

采购中心应回答：哪些订单或生产需求因物料供给存在风险，采购申请和采购订单处于什么阶段，供应商承诺何时交付，已到货数量是否足以关闭缺口，哪些事项需要采购、计划、仓库、品质或有权审批人确认。

目标业务链：

```text
销售订单 / 生产需求 / BOM
  → 物料需求与净缺口
  → 采购申请 / 需求审批
  → 询价、比价与供应商选择
  → 采购订单 / 订单行
  → 供应商确认交期与数量
  → 发货 / 在途
  → 到货、收货、检验与入库
  → 可用库存与缺口关闭
  → 订单交付 / 生产开工影响
  → 采购催办、替代、升级或审批建议（人工确认）
```

一期只允许查询、聚合、解释风险和提出建议，不包含创建或修改采购申请、询价、比价、采购订单、供应商承诺、收货、入库、质检放行、付款、取消或催办消息。AEOS 的分析任务状态不代表中台采购单据已处理，也不代表采购负责人已承诺交期。

金额、供应商选择、替代料、质量处置、对外交期和付款均涉及业务承诺或人工审批。没有经采购负责人确认的价格、币种、税率、订单金额和审批状态时，只能输出数量、日期和缺口事实，不能编造采购金额或节省金额。

## 4. 采购中心技术链路

```text
ERP / SRM / WMS / IQC / SPC 采购相关数据（主责系统待确认）
        ↓ 只读数据供给视图、字段映射和时效标识
SPC 数据供给 API（HMAC + endpoint code + 组织/权限范围）
        ↓
company-control MCP
  输入校验 → 上游调用 → 字段校验 / 脱敏 → 时效 → Evidence
        ↓
AEOS Registry + McpAccessGateway
  白名单 → readOnlyHint → 超时 / 熔断 → 调用审计
        ↓
采购链路聚合层（新增）
  需求 / 缺口 → 采购单据 → 供应商承诺 → 到货 / 可用量
  关联订单、BOM、齐套、库存和质量；检查版本、重复和时效
        ↓
采购中心看板 / Attention / 每日经营问题 / 采购分析任务
        ↓
事项、Evidence、风险或缺口、建议动作、置信度、人工确认角色
```

前端和 Agent 不直接调用 SPC，也不持有 App Secret 或 Bearer Token。Hub 只通过 MCP Gateway 使用 Registry 白名单；采购聚合层不得绕过 Gateway，也不得在 Hub 内部凭缺料数量重新分配库存或自行承诺交期。

## 5. 建议新增的采购 SPC / MCP 契约

**本节 Tool 名称、路径、endpoint code 和字段均为待评审建议，尚未证明中台已经存在。** 正式名称、查询权限、组织范围和签名 code 由中台平台组与采购负责人确认后才能实现。

| 阶段 | 建议 MCP Tool | 建议 GET 路径 | 建议 endpoint code | 主要用途 |
|---|---|---|---|---|
| P0 | `procurement_requisitions_list` | `/external/procurement/requisitions/list` | `procurement.requisitions.list` | 采购申请、审批状态、需求数量与期望到货日期 |
| P0 | `procurement_orders_list` | `/external/procurement/orders/list` | `procurement.orders.list` | 采购订单及订单行、供应商、订购量、承诺日期 |
| P0 | `procurement_receipts_list` | `/external/procurement/receipts/list` | `procurement.receipts.list` | 发货/到货/收货数量、收货日期和关联采购订单 |
| P1 | `procurement_supplier_confirmations_list` | `/external/procurement/supplier-confirmations/list` | `procurement.supplier_confirmations.list` | 供应商确认、变更承诺和确认时间 |
| P1 | `procurement_supplier_performance_list` | `/external/procurement/supplier-performance/list` | `procurement.supplier_performance.list` | 经业务确认的交付、质量和响应表现 |

P0 先打通申请、订单、收货三类只读快照，能够回答“缺口有没有形成采购动作、订单承诺是否覆盖需求、收到多少”。P1 再补充供应商承诺和履约指标。询价、报价、价格比较和付款数据涉及更高敏感度，需单独确认字段分级和授权，不因采购中心上线自动纳入。

### 5.1 公共查询参数

建议所有采购列表 Tool 支持：`page`（从 1 开始）、`page_size`（默认 20，最大 200）、`request_id`（最长 64）、`updated_after`（带时区 ISO 8601，可选）、`org_code`（若存在多组织边界）。日期范围采用成对的 `*_start` / `*_end`，顺序和最大窗口由采购负责人确认。

| Tool | 专用过滤与校验 |
|---|---|
| 采购申请 | `requisition_no`、`material_code`、`demand_no`、`status`、`required_date_start/end`、`buyer_code`；未带条件时必须受限分页，不隐式全库扫描 |
| 采购订单 | `purchase_order_no`、`purchase_order_line_no`、`requisition_no`、`material_code`、`supplier_code`、`status`、`promised_date_start/end` |
| 收货记录 | `receipt_no`、`purchase_order_no`、`material_code`、`supplier_code`、`receipt_date_start/end`、`inspection_status` |
| 供应商承诺 | `purchase_order_no`、`supplier_code`、`confirm_status`、`confirmed_date_start/end` |
| 供应商履约 | `supplier_code`、`material_code`、`period_start/end`、`metric_type`；只允许读取经确认的指标口径 |

`updated_after` 表示源对象更新时间，不等于交期、承诺时间或收货时间。建议全量按稳定主键排序，增量按 `(updated_at, id)` 排序并采用重叠窗口及主键去重。取消、关闭、删除或更正记录必须通过墓碑、版本或对账可见，不能让 Hub 长期保留已失效采购状态。

### 5.2 返回信封与分页

建议沿用当前 SPC `{code,message,data}` 上游信封，由 MCP 统一转换为标准包：

```json
{
  "code": 0,
  "message": "success",
  "data": {
    "items": [],
    "total": 0,
    "data_as_of": "2026-09-28T02:00:00Z",
    "data_confidence": "high",
    "stale": false
  }
}
```

这是协议示意，不是采购业务查询结果。只有过滤范围完整、分页语义明确时，空数组才表示该范围内没有记录。`total` 是过滤后的总数，不是当前页长度；发生截断、源端分页不一致或快照无法保持一致时必须显式降级。

## 6. 建议数据字典与关联约束

本节是采购专用契约的交付要求，不声称现有中台已经具备这些字段。不可得的非关键字段返回 `null` 并说明缺失原因；稳定主键、来源组织、数量单位和关联键缺失时，记录不能进入高置信度风险聚合。

### 6.1 采购需求与缺口

| 字段 | 类型 | 语义 / 约束 |
|---|---|---|
| `demand_id` / `demand_no` / `demand_line_no` | string | 需求稳定主键、展示编号、行号；与订单或生产需求的关系需明确 |
| `source_type` / `source_id` / `org_code` | string | 来源对象和组织边界；不得仅按物料编码跨组织合并 |
| `material_code` / `material_name` / `specification` | string | 物料主数据引用；编码为主键，名称只能展示 |
| `required_qty` / `uom` | decimal / string | 需求数量与单位；不混合采购单位、库存单位和包装单位 |
| `required_date` | date | 业务需求日期；需标注来自订单、生产还是齐套计算 |
| `net_shortage_qty` | decimal / null | 净缺口；应说明现存、锁定、已分配和未来供给的计算口径 |
| `priority` / `status_raw` / `status` | string | 原始优先级、原始状态和签认后的标准状态 |
| `allocation_run_id` / `updated_at` | string / datetime | 齐套或分配批次及源对象更新时间 |

当前 `material_kitting_demands_list` 的需求对象说明为销售订单行；当前 `material_shortages_list` 支持需求单号和物料编码过滤。两者不能直接拼成采购申请，必须由中台提供正式需求到采购动作的关系。

### 6.2 采购申请

最小字段建议为：`requisition_id`、`requisition_no`、`requisition_line_id`、`material_code`、`requested_qty`、`uom`、`required_date`、`requester_org`、`buyer_org`、`approval_status_raw`、`approval_status`、`approved_at`、`source_demand_id`、`source_demand_line_no`、`allocation_version`、`updated_at`。

申请状态必须保留原始值，并由采购负责人签认标准映射，例如 `draft / submitted / approved / rejected / converted / cancelled / unknown`。审批通过不等于已经下达采购订单；申请被驳回、取消或拆分时需能追溯到原申请。

### 6.3 采购订单与订单行

最小字段建议为：`purchase_order_id`、`purchase_order_no`、`purchase_order_line_id`、`line_no`、`supplier_code`、`material_code`、`ordered_qty`、`uom`、`order_date`、`required_date`、`promised_date`、`confirmed_qty`、`status_raw`、`status`、`source_requisition_id`、`source_demand_id`、`currency`、`amount`、`updated_at`。

金额字段默认按敏感字段处理。只有采购负责人和中台安全负责人确认授权、币种、含税/未税和金额口径后，才允许暴露或参与排序。若只开放数量和日期，金额影响标注“未知”，不能用订单销售额替代采购金额。

采购订单必须按订单行主键关联物料和需求；一张采购订单可覆盖多个需求，一条需求也可由多个采购订单分批供给。关联关系应包含 `allocated_qty`、`allocation_version` 或等价字段，否则不能判断某个订单是否真正覆盖某个缺口。

### 6.4 供应商承诺与供给状态

建议字段：`confirmation_id`、`purchase_order_id`、`purchase_order_line_id`、`supplier_code`、`confirmed_qty`、`confirmed_date`、`confirmation_status`、`confirmed_at`、`change_reason`、`revision`、`updated_at`。

现有 `material_supplies_list` 的 `supply_type` 支持 `PURCHASE / OUTSOURCE / PRODUCTION / TRANSFER`，可作为未来供给参考；只有明确 `supply_no`、来源单据、数量、预计可用日期和关联版本后，才能把采购在途与其他供给分开判断。

### 6.5 到货、收货、检验与入库

建议字段：`receipt_id`、`receipt_no`、`purchase_order_id`、`purchase_order_line_id`、`material_code`、`supplier_code`、`shipped_qty`、`received_qty`、`accepted_qty`、`rejected_qty`、`uom`、`arrival_at`、`received_at`、`inspection_status`、`available_at`、`warehouse_code`、`batch_no`、`updated_at`。

发货、到货、收货、检验合格和可用入库是不同事件，不能将任一事件直接当作“缺口已关闭”。若只返回库存聚合，`available_qty` 只能作为当前可用量参考，不能推断某一供应商已完成交付。

### 6.6 与订单、BOM、齐套、质量的关联

关联优先级为：正式需求/采购行关系 > 稳定订单行关系 > BOM 版本关系 > 物料编码展示关系。禁止仅按物料名称、规格相似、供应商名称或订单号前缀推断采购覆盖。

齐套缺料应先确认 `demand_type + demand_no + demand_line_no + allocation_run_id`，再关联采购申请、采购订单和收货。现有销售订单行齐套结果只能说明订单供给背景，不代表采购申请已审批，也不能证明某张采购订单能供给该需求。

质量接口当前可能对 `supplier_code`、`material_code`、`batch_no`、`blocking` 等字段返回 `null`。在没有显式采购行、批次或收货检验关联时，只能输出“存在质量关联缺口”或“需品质确认”，不能输出“供应商质量不合格”或“禁止入库”。

## 7. MCP 返回、Evidence 与数据时效

每个采购 Tool 必须同时声明 `permission_level=READ_ONLY`、Registry `readOnly=true` 和 MCP `annotations.readOnlyHint=true`，严格 Schema 拒绝未定义参数。采购适配器不得接受写操作参数，不得把“催办”或“审批”作为隐藏副作用。

建议 Evidence 实体：`procurement-demand`、`procurement-requisition`、`purchase-order`、`purchase-order-line`、`supplier-confirmation`、`procurement-receipt`、`procurement-supplier`。Evidence ID 要包含来源、组织和稳定对象 ID，并处理 `/`、`@` 等字符转义。

以下仅为**虚构的协议示例，禁止作为业务依据引用**：

```json
{
  "source": "company-control",
  "capability": "procurement_orders_list",
  "read_only": true,
  "generated_at": "2026-09-28T02:01:00Z",
  "data_as_of": "2026-09-28T02:00:00Z",
  "data_confidence": "high",
  "request_id": "example-procurement-001",
  "evidence_refs": [
    "control-platform://purchase-order/EXAMPLE-ORG/EXAMPLE-PO@2026-09-28T02:00:00Z"
  ],
  "data": [{"purchase_order_no": "EXAMPLE-PO", "material_code": "EXAMPLE-MATERIAL", "status": "confirmed"}],
  "page": {"page": 1, "page_size": 20, "total": 1, "truncated": false}
}
```

真实 Agent 结论必须引用本次 MCP 返回的实际 `evidence_refs`，并同时引用需求、采购订单、收货、库存或质量等相关来源。Hub 调用审计与 MCP 业务 Evidence 分别保留，不能互相替代。

当前公共 `list_result()` 每次最多返回 50 个 Evidence。采购一期建议 `page_size<=50`，确保展示记录可以逐项取证；若允许更大页，必须补充分页取证或行级引用，不能为未覆盖的记录编造 Evidence。

当前公共 helper 对缺失 `data_as_of` / `data_confidence` 存在默认兜底行为。采购新适配必须在调用 helper 前校验真实时间和合法置信度：缺失或非法时返回结构化“数据置信度不足”，不能把请求时间补成业务刷新时间，也不能把未知置信度提升为 high。`stale=true` 必须转为 `STALE_DATA` 或按业务确认的降级方案处理。

采购风险分析至少同时检查：来源时效、分页是否完整、需求与采购关联是否完整、采购订单状态、承诺日期、收货数量、库存可用量和质量状态。任一关键来源过期或关联不可信时，结论标记“数据置信度不足”，停止金额、交期或责任归因判断。

## 8. 采购风险识别与计算口径

| 事项 | 必需事实 | 不能做的推断 |
|---|---|---|
| 缺口未形成采购动作 | 同一需求/物料存在可信净缺口，且在确认窗口内没有有效申请或采购订单 | 缺料行没有 `supply_no` 就直接认定采购未发起 |
| 采购申请审批滞后 | 申请已创建、需求日期已临近，审批状态明确且超过业务阈值 | 没有审批时间就用更新时间猜审批滞后 |
| 采购承诺晚于需求 | 采购订单或供应商承诺日期晚于需求日期，关联数量覆盖关系明确 | 预计供给日期晚就归责供应商；未区分采购、委外、自制、调拨 |
| 采购订单未覆盖缺口 | 订单行数量、单位、分配版本与净缺口可比，覆盖量不足 | 把整张采购订单数量分配给所有相同物料需求 |
| 到货不足或收货未可用 | 发货/收货/合格入库数量与采购订单行关系明确 | 到货即当作可用库存，或把检验待定当作合格 |
| 供应商承诺变更 | 同一订单行存在版本化承诺，变更原因和时间可信 | 只比较当前日期而忽略承诺历史 |
| 采购质量风险 | 收货批次、采购行、质量问题之间有显式关系，且 blocking/检验状态明确 | 产品相同或供应商相同就认定该批次不合格 |
| 金额暴露 | 已授权、含义明确的采购金额和币种，且关联去重 | 用销售订单金额、单价缺失或不同币种金额代替采购损失 |

建议计算：

- 采购覆盖率 = 已确认有效采购数量 / 净缺口数量。分母缺失、为 0、单位不一致或分配版本缺失时返回未知；不把采购申请数量当作已到货数量。
- 未交数量 = 采购订单行数量 − 已确认收货或有效入库数量，必须按订单行、批次和更正口径去重；没有统一单位时不计算。
- 交期偏差 = 可信承诺/预计可用日期 − 需求日期。没有业务日历时先按自然日展示并标注口径；节假日、运输缓冲和检验周期由采购负责人确认。
- 采购订单金额、逾期概率、实际损失和客户承诺不能由 Hub 自行估算。没有正式概率模型时，使用“已确认/待确认/未知”状态和 P0/P1/P2 分级，不把颜色映射成概率。
- 多条缺料、采购订单或收货记录关联同一订单时，对订单、采购订单和需求对象分别去重；金额影响只有在明确口径后才按“金额 × 概率 × 时效”排序。

## 9. Hub 接入及页面交付

### 9.1 建议查询流程

1. 检查 Registry 与实时 `tools/list`，确认采购专用能力是否已登记并可用；health 成功不足以证明采购端点可用。
2. 按组织、需求日期和物料范围读取缺料/齐套结果，记录 `data_as_of`、`data_confidence`、分页总数和截断状态。
3. 对候选缺口查询采购申请、订单和收货，优先按稳定需求 ID、订单行 ID 或采购订单行 ID 关联，限制并发和总时间预算。
4. 复用物料、供应商、库存和未来供给 Tool；严格遵守真实 Schema，不把采购过滤字段传给尚未支持的现有 Tool。
5. 检查单位、数量、状态、版本、日期、时效和 Evidence 覆盖，再计算覆盖率或交期偏差。
6. 展示事实、缺口、建议动作和人工确认角色；不向中台下发采购指令，不声称已催办、已审批或已处理。

一期优先按需查询，避免把全量采购单据复制到 Hub。缓存键需包含组织/权限范围、过滤条件、页码和数据版本；缓存内容显示采集时间。达到分页或时间预算时标记“部分数据”，不得显示全量采购风险总数。

## 10. 鉴权与错误处理

沿用现有 HMAC 请求头 `X-App-Key`、`X-Timestamp`、`X-Signature`。签名材料为 `timestamp + app_key + endpoint_code + query_string`，使用 HMAC-SHA256。必须复用现有查询串构造逻辑，确保签名 code、参数编码、顺序与实际请求一致。

采购新增 endpoint code 需要中台管理员为部署 Key 授权，并确认组织范围、来源系统和调用主机 IP。凭证只由部署环境注入，不放入文档、浏览器、提示词、日志、Evidence 或审计正文。

| 场景 | 处理要求 |
|---|---|
| 400/422 | `INVALID_ARGUMENT`，说明可修复字段，不重试 |
| 401/403 | `UNAUTHORIZED/FORBIDDEN`，提示认证或授权问题，不无限重试 |
| 404 | 现有映射为 `NOT_FOUND`；采购列表端点 404 是能力异常，不转空列表 |
| 端点未开放 | `UPSTREAM_UNAVAILABLE` 且 `retryable=false`，明确“能力未开放” |
| 超时、429、5xx | 复用有限重试和 Gateway 熔断；最多首次加一次重试 |
| 返回结构不合规 | 显式失败或记录隔离并标记不完整，不默认为成功空数组 |
| `stale=true` / 时效不明 | 标记“数据置信度不足”，停止交期、金额和责任判断 |
| 某来源失败 | 保留其他可用域，明确缺少的来源及对结论的影响 |

标准错误信封当前不一定回显 `request_id`；如采购链路需要错误级追踪，应同步更新契约和测试，不能在验收时假定已支持。

## 11. 联调与验收用例

下列为开发完成后的验收要求，不是本次已运行结果。

| 用例 | 预期 |
|---|---|
| 已授权 Key 查询申请、采购订单、收货 | 数据、数量、状态、关联主键、时效和原始记录一致 |
| 缺少授权 / 签名 endpoint code 错误 | 明确错误，不返回空成功 |
| 未知字段、非法日期、反向区间、超大页 | Schema 或参数校验拒绝 |
| 全部新增采购 Tool | `READ_ONLY`、运行时 `readOnlyHint`、Registry 和 `server.json` 一致 |
| 一申请多订单、一订单多需求 | 关联准确，覆盖数量和金额不重复 |
| 部分交货、分批收货、退货或更正 | 按订单行和修订口径正确计算，不重复计数 |
| 单位不一致、零需求量、超收 | 未知或异常标识，不除零、不混单位 |
| 供应商承诺日期变更 | 保留版本和变更时间，不能只显示最后值而丢失追溯 |
| 质量 blocking=null 或没有采购行关联 | 不自动认定供应商不合格或禁止入库 |
| 现有销售行缺料但无采购关系 | 不自动判定采购未发起，也不声称供应商逾期 |
| 51 条以上记录与多页结果 | 每条被引用记录有有效 Evidence，截断可见 |
| 时间缺失、过期、跨源时间差过大 | 不补造高置信度，按来源降级并停止高风险判断 |
| 成功空结果 vs 截断结果 | 分别显示范围内无记录和部分覆盖 |
| 指标 Tool 返回 `UPSTREAM_UNAVAILABLE` | 说明端点未开放，不解读为采购指标为零 |
| 单一端点超时或 404 | 其他链路仍可用，采购来源显示不可用 |
| 采购分析任务分派 | 采购角色校验生效；旧订单、齐套、质量任务仍可读取 |
| 旧订单、物料、供应商、齐套查询 | 名称、参数、返回和只读边界兼容 |

建议验证命令：仓库根执行 `npm run check:types`、`npm run test:mcp-policy`、`npm run test:dashboard`、`npm run test:pagination`；在 `mcp-company-control/` 执行 `python scripts/test_company_control.py`。新增采购测试接入 `package.json` 后再执行。Mock 通过不能替代真实 SPC 联调。

验收记录应附：脱敏请求与响应、正式 endpoint code、字段映射、状态枚举、至少一条“缺口—采购订单—收货”完整证据链、至少一条异常链路、分页和时效结果、敏感字段评审、采购负责人意见。完成记录后才能把“待联调”改为“已验收”。

## 13. 上线、监控与回退

建议上线顺序：SPC 先发布并验证 P0 只读端点 → 授权部署 Key → 发布兼容 MCP 包 → 同步 Registry 和元数据 → 核对 `tools/list` → 灰度开启采购视图 → 采购/计划/仓库/品质 Owner 对照真实链路验收 → 扩大使用范围。

建议监控：调用成功率、耗时、认证失败、分页截断、数据年龄、缺失主键比例、需求未关联采购比例、采购订单未关联收货比例、数量单位异常、Evidence 覆盖率、端点版本不一致和 stale 数据比例。报警阈值及负责人由运维和业务共同确认。

回退优先关闭采购视图和采购任务入口，撤去新增采购 Tool 的调用依赖；如禁用 Tool，必须同步 Registry、MCP 元数据和运行实现，避免清单校验失败。需要版本回退时回退成套兼容版本，保留已有订单、物料、齐套、库存、质量和生产能力及历史 Evidence。不得删除历史证据来消除错误记录。

## 14. Agent 结论模板与人工确认

```text
事项：<需求/物料/采购订单行及具体偏差>
依据：<本次 MCP 真实返回的 evidence_refs，按需求、采购、收货、库存、质量分别列出>
风险/缺口：<数量、日期、金额、概率；缺失写未知>
建议动作：<采购/计划/仓库/品质/审批角色做什么、何时完成；注明审批人>
置信度：高/中/低；<数据时效、关联完整性、字段缺失、分页覆盖原因>
```

建议分级：P0 为已确认影响当前生产或客户交付且需立即核实的事项；P1 为近期缺口、承诺偏差或收货异常待确认；P2 为字段、时效、授权和关联缺口。此分级是建议规则，需采购负责人确认。下单、改期、供应商切换、替代料、价格和对外交期承诺必须由有权业务负责人审批；收货和质量放行由仓库/品质负责人确认。

本稿无实时采购业务 Evidence，不能填写实际采购金额、供应商逾期概率或真实 TOP 风险。下一节列出的是开发交接关注项，按上线依赖排列；金额和概率未知时不做经营风险乘积排序。

## 15. TOP 需人关注事项（最多 5 条）

| 事项 | 依据 | 风险 / 缺口 | 建议动作与确认角色 | 置信度 |
|---|---|---|---|---|
| 1. 确认采购专用只读端点 | 当前 21 个 Tool 中没有采购申请、采购订单、收货专用 Tool；无业务 `evidence_ref` | 采购中心只能看到缺料和未来供给，无法证明采购阶段；金额/概率未知 | 中台平台组与采购负责人在 D0/D1 确认正式 API、endpoint code、权限和样例 | 高：本地 Tool 缺口已核验；线上状态待确认 |
| 2. 确认需求到采购订单行的稳定关联 | 现有齐套需求和缺料 Tool 以销售订单/物料为主；无采购订单行 Evidence | 可能把同物料不同需求错误合并，导致覆盖率和逾期判断失真 | 采购、计划和 SPC 在 D0 签认需求、申请、订单行、分配版本和拆分规则 | 高：现有输入约束明确；业务关联未验证 |
| 3. 确认到货、收货、检验和可用库存口径 | 当前只有库存聚合和未来供给参考；无收货/检验专用接口 | 到货可能被误判为可用，采购缺口可能被错误关闭 | 仓库、品质、采购负责人在 D0/D4 确认事件顺序、数量单位和退货/更正口径 | 高：现有 Tool 边界已核验；业务字段待确认 |
| 4. 确认金额、供应商履约与质量权限 | 当前敏感金额字段会脱敏；质量数据部分供应商/物料关联字段可能为 null | 无法可靠排序金额影响、归责供应商或判断质量放行 | 中台安全负责人、采购和品质负责人确认字段分级、授权和人工审批边界 | 中：安全约束明确；业务口径未确认 |
| 5. 补齐真实时效与逐项 Evidence | 公共列表 Evidence 每次最多 50 条，新适配需防止时效默认兜底 | 过期或未覆盖数据可能被输出为高置信度采购结论 | MCP/AEOS 开发在 D2/D3 加严格时效、分页、关联和 Evidence 测试，由测试负责人验收 | 高：本地实现约束已核验；采购数据尚未联调 |
