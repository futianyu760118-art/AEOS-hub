# 港湾存储改造决策（2026-10-23）

> 背景：B 版评审指出 `data/ai-harbor.json` 单文件快照写放大。本文给出事实、选项和拍板结论，作为第 1 步（网关试点）的并行任务依据。

## 1. 现状事实

| 指标 | 数值 |
|---|---:|
| 文件 | `data/ai-harbor.json` |
| 大小 | 约 36KB |
| `revision` | **27015**（B 稿写作时 26346） |
| Agent 数 | 14（1 L0 + 13 L1） |
| 写入方式 | 每次状态变更 `atomicWrite` 整个 JSON 快照 |

**判断：** 当前 14 个 Agent 就产生了明显的写放大；接入网关后（roster 同步 + 系统级心跳）写入频率只会更高。这不是“以后再说”的问题，应进入第 1 步并行任务。

## 2. 三个选项

| 方案 | 做法 | 成本 | 收益 | 风险 |
|---|---|---|---|---|
| **A. 降写频率** | 状态变更 debounce/批量写；心跳只更新内存，不落盘；定期快照 | 低（0.5~1 人天） | 立刻降低写放大 | 进程崩溃可能丢最近几秒状态；可接受 |
| **B. 分文件/增量写** | 按 system 或 agent 分文件；只写变更；索引文件记录版本 | 中（2~4 人天） | 写放大与 Agent 数解耦 | 需要迁移脚本、一致性校验 |
| **C. SQLite** | 状态、借调单、用量分表；WAL + 定期快照 | 高（5~10 人天） | 最适合大规模、支持查询 | 引入新依赖、迁移与备份复杂 |

## 3. 拍板结论

**第 0a 步：不写代码，只定方案。**

**第 1 步：先做 A，再评估 B；C 作为规模选项。**

具体：

1. **A 立即做**：心跳不落盘；状态变更 1~2 秒 debounce 批量写；保留退出前强制 flush。
2. **B 在网关试点前评估**：如果单系统 Agent 数 > 30，或峰值写入 > 5 次/秒，就上分文件/增量写。
3. **C 暂不做**：当 Agent > 100，或峰值写入 > 10 次/秒，或需要按 Agent 查询历史时，再迁 SQLite。
4. 无论选哪个，借调单、用量、证据仍保持现有独立文件，不混进港湾状态。

**理由：**

- A 成本最低，能先止血；
- B 与网关试点天然配套，可按系统分片；
- C 对当前 14 个 Agent 过重，且会引入新的运维面；
- 先做 A/B 不阻塞网关契约和试点。

## 4. 验收口径

| 指标 | 目标 |
|---|---|
| 港湾状态峰值写入 | < 10 次/秒 |
| 单次状态变更写盘量 | 不再整体重写（A 阶段至少做到批量） |
| 进程崩溃恢复 | 最多丢 2 秒状态；借调单/用量/证据不丢 |
| 迁移回滚 | 保留变更前备份；可回滚到 JSON |
| 一致性 | 分文件后，索引与分片可校验 |

## 5. 实施落点（第 1 步）

- `src/harbor-store.ts`：写入入口增加 debounce/flush；按需拆分文件。
- `src/atomic-file.ts`：保持原子写；增加批量写辅助。
- `src/server.ts`：进程退出前 flush；启动时校验索引。
- `scripts/`：新增迁移/校验脚本，默认干跑，`--apply` 需先停 Hub。
- 测试：并发写、崩溃恢复、迁移校验、回滚。

## 6. 不在本期做

- 不把借调单、用量、证据迁进港湾存储；
- 不做跨实例共享存储（留给高可用阶段）；
- 不做在线迁移（Hub 需停机或进入只读窗口）。
